# StoryFlow AI — 项目详细介绍

## 一、项目概述

StoryFlow AI 是一个基于 **StoryFlow Runtime V3.5** 的 AI 漫剧自动生成平台。用户只需输入一段创意描述（如"一个现代女孩穿越到古代的奇幻冒险故事"），系统就会通过 7 个专业 AI Agent 的协作，自动完成从剧本创作到最终视频导出的全流程，输出可播放的 MP4 漫剧视频。

这个项目的核心价值不仅在于"能生成漫剧"，更在于其底层构建的 **通用 AI Runtime 平台**。Runtime 提供了工作流编排（Workflow DSL）、策略化重试（RetryEngine）、四层共享记忆（MemoryRuntime）、全链路追踪（TraceRuntime）、多 Agent 协作调度、事件驱动通信、可插拔模型后端、质量闭环检查、局部重生成等一系列基础能力。理论上，只需替换 Agent 和 Workflow DSL，这个 Runtime 就能驱动任何多步骤、多 Agent 协作的 AI 内容生成场景——小说创作、广告视频、动画制作等。

### 核心定位

- **对用户**：输入创意 → 一键生成漫剧视频，零门槛
- **对开发者**：一个可扩展的 AI Runtime 框架，通过 YAML DSL 定义工作流，通过 Agent SDK 扩展新能力
- **对运维**：云端 API + Mock 降级，只需配一个 LLM Key 就能跑通全流程

### 2.2 Runtime 能力矩阵

| 能力 | 组件 | 说明 |
|------|------|------|

| **智能决策** | DirectorAgent | 观察-思考-决策模式，集成 RetryEngine 联动 |
| **任务规划** | PlannerAgent | 需求拆解为 Task DAG，支持 5 种预置管线 |
| **事件通信** | EventBus (pub/sub) | 16 种事件类型，组件完全解耦 |
| **共享状态** | Blackboard | 点号路径读写（如 `scenes.0.status`），变更自动广播 |
| **中间产物** | ArtifactManager | 文件化存储 + 每步自动 Checkpoint |
| **会话管理** | SessionManager | 跟踪已完成步骤，支持局部重生成 |
| **横切扩展** | HookFramework | Before/After/Error 三类 Hook，支持全局和步骤级 |
| **模型切换** | AdapterRegistry | 改配置换模型，Agent 代码不动 |
| **Agent 扩展** | Agent SDK | 继承 BaseAgent，实现 execute()，一行注册 |

### 2.3 核心设计原则

**Agent 隔离原则**：Agent 只接收输入（state dict）、返回输出（result dict），**禁止互相调用**。所有 Agent 之间的数据传递和调度由 Runtime 统一管理。这意味着：

- Agent 不需要知道上下游 Agent 的存在
- 可以独立测试任何一个 Agent
- 替换/新增 Agent 不影响其他 Agent

**Runtime 唯一调度权**：WorkflowEngine 是唯一的执行引擎，通过 YAML DSL 定义步骤和依赖关系，决定哪些步骤串行、哪些并行。

## 三、Runtime 核心组件详解

### 3.1 StoryFlowRuntime（主入口）

`runtime/core.py` 中的 `StoryFlowRuntime` 类是整个 Runtime 的门面（Facade），它组装了所有子系统，提供三个核心 API：

```python
runtime = StoryFlowRuntime()
runtime.register_existing_agents()

# 1. 创建会话
session = runtime.create_session(story_id="...", prompt="...", genre="...")

# 2. 运行完整管线
result = await runtime.run(session.id)

# 3. 局部重生成（只重跑 image 及之后的步骤）
result = await runtime.rerun_step(session.id, "image")
```

内部使用全局单例模式（`get_runtime()`），FastAPI 启动时初始化。

### 3.2 EventBus（事件总线）

`runtime/event_bus.py` 实现了异步发布/订阅模式，是所有组件解耦通信的基础。

**16 种事件类型**：

| 分类 | 事件 | 触发时机 |
|------|------|---------|
| 会话生命周期 | `SESSION_CREATED` / `SESSION_COMPLETED` / `SESSION_FAILED` | 会话状态变更 |
| 步骤生命周期 | `STEP_STARTED` / `STEP_COMPLETED` / `STEP_FAILED` / `STEP_RETRY` | 每个管线步骤 |
| 产物 | `ARTIFACT_SAVED` / `ARTIFACT_LOADED` | 文件存取 |
| 状态 | `BLACKBOARD_CHANGED` | Blackboard 数据变更 |
| 质量 | `QUALITY_CHECK` / `QUALITY_PASS` / `QUALITY_FAIL` | 质量检查结果 |
| 决策 | `DIRECTOR_DECISION` / `DIRECTOR_INTERVENE` | Director 做出决策 |
| 重试 | `STEP_RETRY` | RetryEngine 发起重试 |
| 规划 | `PLAN_CREATED` / `PLAN_UPDATED` | Planner 生成/更新计划 |

实现特点：
- `asyncio.gather()` 并发通知所有订阅者，单个 handler 出错不影响其他
- 内置事件历史（cap 1000），支持查询
- 全局单例 `get_event_bus()`

**典型事件链**：
```
WorkflowEngine 执行 image 步骤
  → publish(STEP_STARTED, {step: "image"})
  → image_agent 执行
  → ArtifactManager 保存图片 → publish(ARTIFACT_SAVED)
  → QualityEngine 检查 → publish(QUALITY_PASS/FAIL)
  → publish(STEP_COMPLETED, {step: "image"})
  → DirectorAgent 收到 STEP_COMPLETED → 重置重试计数
```

### 3.3 Blackboard（共享黑板）

`runtime/blackboard.py` 实现 AI 黑板模式（Blackboard Pattern），Agent 通过读写共享状态交换数据，而非直接互相调用。

**核心特性**：
- **点号路径访问**：`blackboard.set("scenes.0.image_url", "/path/to/img.png")` 支持嵌套 dict 和 list 索引
- **自动创建中间容器**：写入 `scenes.0.status` 时，如果 `scenes` 不存在会自动创建
- **变更广播**：每次 `set()` 操作自动通过 EventBus 发布 `BLACKBOARD_CHANGED` 事件
- **快照/恢复**：`get_snapshot()` / `load_snapshot()` 用于 Checkpoint 机制

每个 Session 创建独立的 Blackboard 实例，保证会话间隔离。

### 3.4 ArtifactManager（产物管理器）

`runtime/artifact_manager.py` 将每个步骤的中间产物文件化存储到磁盘，目录结构如下：

```
artifacts/
└── {session_id}/
    ├── script/
    │   └── script_output.json          # 剧本结构化输出
    ├── character/
    │   └── characters_enriched.json    # 角色视觉描述
    ├── storyboard/
    │   └── storyboard_output.json      # 分镜列表
    ├── image/
    │   └── scene_001.png               # 逐场景图片
    ├── voice/
    │   └── scene_001.wav               # 逐场景配音
    ├── video/
    │   └── story.mp4                   # 最终视频
    └── _checkpoints/
        ├── step_script_20260628_072930.json
        └── step_image_20260628_073145.json
```

**关键能力**：
- 每步完成后自动保存 Checkpoint（包含完整 state 快照）
- `load_latest_checkpoint()` 支持断点恢复
- `list_artifacts()` 可查询某 Session 的所有产物
- `get_completed_steps()` 返回已完成的步骤列表
- `cleanup_session()` 清理过期数据

**局部重生成的基础**：当用户要求"重新生成第 3 幕的图片"时，Runtime 从 ArtifactManager 加载 script/character/storyboard 的已保存结果，只从 image 步骤开始重新执行。

### 3.5 SessionManager（会话管理器）

`runtime/session_manager.py` 跟踪每个生成会话的状态，支持 6 种状态：

```
PENDING → RUNNING → COMPLETED
                  → PAUSED → RUNNING（恢复）
                  → FAILED
                  → CANCELLED
```

**核心方法**：
- `create()` — 创建会话，生成 8 位短 ID
- `complete_step()` / `fail_session()` — 状态转换
- `reset_from_step(step)` — **局部重生成的关键**：移除目标步骤及之后所有已完成步骤
- `get_by_story(story_id)` — 查找故事的最近会话
- `cleanup_old_sessions(max_age_hours=24)` — 自动清理

### 3.6 WorkflowEngine（工作流引擎）

`runtime/workflow_engine.py` 是 Runtime 的心脏，负责执行管线。内部集成了 RetryEngine、MemoryRuntime、TraceRuntime，每个步骤的执行都经过完整的 Runtime 能力包装。支持两种执行模式：

#### 线性执行

```
script → character → storyboard → image → voice → video
```

每个步骤完成后自动跳过已完成的步骤（用于重生成场景）。

#### Wave 并行执行

从 YAML DSL 解析依赖关系，生成"执行波"（Execution Waves）：

```
Wave 1: [script, character, storyboard]     # 串行依赖链
Wave 2: [image, voice]                      # parallel_group: media_generation
Wave 3: [video]                             # 依赖 image + voice
```

Wave 2 中的 image 和 voice 通过 `asyncio.gather()` 并发执行。

#### 单步执行的完整流程

每个步骤的执行都经过完整的 Runtime 能力链：

1. **构建 StepContext** — 封装步骤名、会话 ID、Blackboard、ArtifactManager
2. **启动 Trace Span** — `trace.start_span(step_name)` 开始计时
3. **发布 STEP_STARTED** — 通知所有订阅者
4. **运行 Before Hooks** — 可修改 StepContext 或中止
5. **调用 Agent** — `agent_func(state)` 执行实际工作
6. **结束 Trace Span** — 记录耗时、Token、费用
7. **保存 Artifacts** — 结果持久化到磁盘
8. **更新 Blackboard** — 写入共享状态
9. **同步 Memory** — `memory.populate_from_state()` 更新四层记忆
10. **运行 After Hooks** — 可修改结果
11. **质量检查** — 如果启用，运行 QualityEngine；失败则咨询 Director
12. **发布 STEP_COMPLETED** — 通知所有订阅者
13. **错误处理** — 通过 RetryEngine 统一处理重试/降级/终止（见 3.13 节）

### 3.7 DirectorAgent（导演 Agent）

`runtime/director.py` 实现了"只决策、不生成内容"的设计理念。Director 观察 Runtime 的执行过程，在出现问题时做出决策。

**7 种决策类型**：

| 决策 | 含义 | 典型场景 |
|------|------|---------|
| `CONTINUE` | 继续下一步 | 正常完成 |
| `RETRY` | 重试当前步骤 | 网络超时、限流 |
| `ROLLBACK` | 回退到上游步骤 | 质量严重不达标 |
| `SKIP` | 跳过当前步骤 | 内容安全过滤触发 |
| `MODIFY_AND_RETRY` | 修改参数后重试 | 多次重试失败 |
| `ABORT` | 终止管线 | API Key 无效 |
| `HUMAN_REVIEW` | 暂停等待人工 | 需要人工判断 |

**错误模式匹配**：Director 根据异常类型自动分类处理——

```
timeout         → RETRY (置信度 0.85)
rate_limit      → RETRY (置信度 0.90)
api_key/auth    → ABORT  (置信度 0.95)
content_filter  → SKIP 或 ROLLBACK (置信度 0.70)
```

**质量失败处理**：根据质量评分决定策略——

```
score >= 0.7  → RETRY（接近通过，再试一次）
score <  0.3  → ROLLBACK（严重不达标，回退上游）
其他           → RETRY (置信度 0.6)
```

### 3.8 PlannerAgent（规划 Agent）

`runtime/planner.py` 将用户的高层需求拆解为可执行的任务 DAG。

**5 种预置管线**：

| 类型 | 步骤 |
|------|------|
| `comic`（漫剧） | script → character → storyboard → image → image_to_video → voice → video |
| `novel`（小说） | script → character → chapter_outline → text_generation |
| `animation`（动画） | script → character → storyboard → image → image_to_video → voice → video |
| `ad`（广告） | script → storyboard → image → image_to_video → voice → video |
| `movie`（电影） | script → character → storyboard → image → image_to_video → voice → video |

Planner 还为每个 TaskNode 定义了 `input_keys` 和 `output_keys`，清晰标记数据流向。

### 3.9 QualityEngine（质量引擎）

`runtime/quality/__init__.py` 提供结构化的多维度质量检查，每个 Checker 确定性返回检查结果：

```python
QualityResult(
    artifact_type="script",
    passed=True,
    score=0.9,        # 0~1
    issues=[],         # 必须修复的问题
    warnings=["outline 偏短"],  # 建议性问题
    details={...}
)
```

**6 个内置 Checker**：

| Checker | 检查内容 | 评分扣分规则 |
|---------|---------|-------------|
| `ScriptQualityChecker` | 大纲长度、角色数量、集数、每集结构 | 大纲 < 50字 -0.3, 角色 < 2 -0.3, 无集数 -0.4 |
| `CharacterQualityChecker` | 角色四维外观完整性 | 每缺一个维度 -0.1/角色 |
| `StoryboardQualityChecker` | 场景数量、Prompt 长度、时长合理性 | < 3场景 -0.3, Prompt < 20字 -0.2 |
| `ImageQualityChecker` | 图片文件是否存在 | 文件不存在直接 FAIL |
| `VoiceQualityChecker` | 音频文件是否存在 | 文件不存在直接 FAIL |
| `ConsistencyQualityChecker` | 分镜是否引用角色名 | < 50% 引用率 -0.3（跨产物检查） |

每个 Checker 返回的 `QualityResult` 包含 `suggestions` 字段，提供**可操作的修复建议**（如"Expand the outline with more plot details"），这些建议可以在 V4 的 Prompt Runtime 中自动注入到重试 Prompt 中。

### 3.10 RetryEngine（策略重试引擎）

`runtime/retry_engine.py` 实现了**Agent 不自己 retry，Runtime 统一 retry**的核心设计。所有重试逻辑从 Agent 代码中剥离，由 RetryEngine 集中管理。

**设计理念**：
- Agent 只管执行，抛出异常即可
- RetryEngine 根据异常类型自动匹配策略
- 策略定义了"重试几次、退避多久、最终怎么办"
- 每种策略是一个 `RetryPolicy`，包含有序的 `actions` 列表

**5 种 RetryAction**：

| 动作 | 含义 | 说明 |
|------|------|------|
| `RETRY_SAME` | 相同参数重试 | 最常用的重试方式 |
| `MODIFY_PROMPT` | 修改 Prompt 后重试 | LLM 自动调整输入（V4 实现） |
| `SWITCH_MODEL` | 切换模型后重试 | 路由到备用模型（V4 实现） |
| `FALLBACK` | 降级为 Mock 输出 | 返回空 dict + success=True |
| `ABORT` | 终止 | 返回 success=False |

**Action 列表语义**：最后一个 action 是**终极动作**（terminal），前面的是逐次重试策略。例如 `[RETRY_SAME, RETRY_SAME, FALLBACK]` 表示前两次相同参数重试，第三次降级。

**6 种内置策略 + 1 个兜底**：

| 策略名 | max_retries | backoff | 终极动作 | 典型场景 |
|--------|-------------|---------|---------|--------|
| `timeout` | 3 | 2s^attempt, max 10s | ABORT | LLM 响应超时 |
| `rate_limit` | 5 | 4s^attempt, max 30s | ABORT | API 限流 429 |
| `api_error` | 3 | 2s^attempt, max 30s | FALLBACK | 服务器 500/502 |
| `quality_fail` | 2 | 3s^attempt, max 30s | ABORT | 质量检查不通过 |
| `auth_error` | 0 | — | ABORT | API Key 无效 |
| `content_filter` | 1 | 2s^attempt, max 10s | ABORT | 内容安全过滤 |
| `_default` | 3 | 2s^attempt, max 30s | ABORT | 兜底策略 |

**错误自动分类**：RetryEngine 通过关键词匹配异常信息自动选择策略——

```
"timeout" / "timed out"           → timeout
"rate limit" / "429"            → rate_limit
"500" / "502" / "server error"  → api_error
"auth" / "401" / "403"          → auth_error
"content_filter" / "blocked"    → content_filter
其他                           → _default
```

**指数退避 + 抖动**：`wait = min(backoff_base ^ attempt, backoff_max) * (0.5 + 0.5 * random())`，防止多步骤同时重试引发"惊群效应"。

**Director 联动**：每次重试前咨询 DirectorAgent，如果 Director 投票 ABORT，则直接终止。Director 的决策是建议性的，RetryEngine 仍然尊重策略的硬性限制。

**统计 API**：

```python
retry_engine.get_stats()
# → {
#     "total_retries": 5,
#     "total_successes_after_retry": 4,
#     "total_fallbacks": 1,
#     "total_aborts": 0,
#     "policy_usage": {"timeout": 3, "api_error": 2},
#     "registered_policies": ["timeout", "rate_limit", ...]
# }
```

### 3.11 MemoryRuntime（四层记忆系统）

`runtime/memory/` 实现了四层记忆架构，确保所有 Agent 在执行时不仅收到原始 Prompt，还能获得与当前步骤相关的上下文信息。这是实现角色一致性、世界观连贯性的关键基础设施。

**四层记忆结构**：

| 层 | 文件 | 职责 | 生命周期 |
|----|------|------|---------|
| **SessionMemory** | `session_memory.py` | 当前执行的步骤、重试次数、运行时状态 | 会话级，管线结束即清除 |
| **CharacterMemory** | `character_memory.py` | 角色结构化数据（外观、性格、声音） | 会话级，角色 Agent 完成后写入 |
| **WorldMemory** | `world_memory.py` | 世界观设定（时代、地点、规则、氛围） | 会话级，从用户输入和剧本中提取 |
| **TimelineMemory** | `timeline_memory.py` | 有序事件/进度历史 | 会话级，逐步追加 |

**按 Agent 类型自动切片**：`build_context(agent_name)` 根据不同 Agent 的需求返回不同的记忆片段：

| Agent | 获得的记忆 |
|-------|----------|
| `script` | World Settings + Characters（名字+性格）+ Recent Timeline |
| `character` | World Settings + Characters（完整信息） |
| `storyboard` | Characters + World + Recent Timeline（全量） |
| `image` | **Character Appearances**（专门为图片生成格式化的外观描述） |
| `image_to_video` | 最少（仅场景数量） |
| `voice` | **Voice Mapping**（角色名→性别→音色） |
| `video` | 最少（仅 Timeline） |

**关键设计**：

```python
memory = MemoryRuntime(session_id="abc123")

# Character Agent 完成后，自动同步角色数据
memory.populate_from_state(state)
# → characters 列表写入 CharacterMemory
# → genre/prompt 写入 WorldMemory
# → storyboard 场景写入 TimelineMemory

# Image Agent 执行时，自动获得角色外观描述
ctx = memory.build_context("image")
# → "[World Settings]\n"
# → "[Character Appearances (for image generation)]\n"
# → "林晓: long flowing black hair, white summer dress...\n"
```

`CharacterMemory` 提供了 `get_appearance_prompt(name)` 方法，将四维外观（hair/body/cloth/face）拼接为图片生成优化的英文 Prompt 字符串，确保 Image Agent 获得可直接使用的角色描述。

### 3.12 TraceRuntime（全链路追踪）

`runtime/trace/__init__.py` 实现了类似 OpenTelemetry 的全链路追踪系统，记录管线执行的完整过程，用于调试、性能分析、成本核算和前端可视化。

**核心数据结构**：

- **Span** — 单个执行单元的记录，包含：
  - `span_id` / `trace_id` / `parent_id`（支持树状结构）
  - `name` / `step`（Agent 名称和步骤名）
  - `start_time` / `end_time` / `duration_ms`
  - `status`（running / completed / failed / skipped）
  - `tokens_in` / `tokens_out` / `cost` / `model`
  - `retry_count` / `attempt` / `error`
  - `input_summary` / `output_summary`

- **TraceTree** — 一次管线执行的完整 Span 树：
  - `total_duration_ms` — 总耗时
  - `total_tokens` — 总 Token 数
  - `total_cost` — 总费用
  - `span_count` — Span 数量
  - `get_children(parent_id)` — 查询子 Span

**使用方式**：

```python
trace = TraceRuntime()

# 自动在 WorkflowEngine.run() 中启动
trace_id = trace.start_trace(session_id="abc123", metadata={"prompt": "..."})

# 每步自动 start_span / end_span
span = trace.start_span("image", trace_id=session_id, step="image")
# ... agent 执行 ...
trace.end_span(span.span_id, status="completed",
                output_summary={"images": 7},
                tokens_in=0, tokens_out=0, cost=0.15)

# 获取完整追踪树（用于前端可视化）
tree = trace.get_trace("abc123")

# 获取扁平化摘要
summary = trace.get_trace_summary("abc123")
# → {
#     "trace_id": "abc123",
#     "total_duration_ms": 278700.0,
#     "total_tokens": 4800,
#     "total_cost": 0.586,
#     "steps": [
#         {"step": "script", "duration_ms": 2300, "tokens": 1200, "cost": 0.003, "status": "completed"},
#         {"step": "image", "duration_ms": 32000, "tokens": 0, "cost": 0.21, "status": "completed", "retries": 1},
#         ...
#     ]
# }
```

**与 WorkflowEngine 集成**：WorkflowEngine 在每步执行时自动创建 Span，在步骤完成或失败时关闭 Span。RetryEngine 的重试次数也会记录到 Span 的 `retry_count` 字段中。Trace 数据可通过 `/api/runtime/stats` API 返回给前端进行可视化展示。

**生命周期管理**：`cleanup_old_traces(max_age_seconds=3600)` 自动清理超过 1 小时的旧追踪数据，防止内存泄漏。

### 3.13 HookFramework（钩子框架）

`runtime/hooks.py` 允许在不修改 Agent 代码的前提下注入横切逻辑。

**三类 Hook**：

```python
hooks = HookFramework()

# Before Hook — 可修改 StepContext 或抛出 HookAbort 中止
@hooks.before("image")
async def add_negative_prompt(ctx: StepContext):
    ctx.set("negative_prompt", "nsfw, low quality, blurry")
    return ctx

# After Hook — 可修改 Agent 返回结果
@hooks.after("script")
async def log_script_length(ctx, result):
    logger.info(f"Script length: {len(result.get('outline', ''))}")
    return result

# Error Hook — 返回错误处理策略
@hooks.on_error("*")  # 全局 error hook
async def global_error_handler(ctx, error):
    return ErrorAction.RETRY
```

支持步骤级（`"image"`）和全局级（`"*"`）注册，全局 Hook 优先执行。

### 3.14 AdapterRegistry（模型适配器）

`runtime/adapters/__init__.py` 实现策略模式，通过配置切换 AI 模型后端，Agent 代码不动。

**5 类适配器**：

| 适配器 | 可选 Provider | 说明 |
|--------|-------------|------|
| `LLMAdapter` | 任何 OpenAI 兼容 API | 自动路由 creative/precise 模型 |
| `ImageAdapter` | `dashscope` / `openai` / `mock` | 文生图（云端 API） |
| `VoiceAdapter` | `dashscope_tts` / `mock` | TTS 语音合成（云端 API） |
| `I2VAdapter` | `kling` / `runway` / `mock` | 图生视频（云端 API） |
| `VideoAdapter` | `ffmpeg`（本地合成） | 视频拼接 + 字幕烧录 |

切换模型只需改环境变量：

```bash
# 切换图片后端
IMAGE_API_PROVIDER=dashscope   # 通义万相
IMAGE_API_PROVIDER=openai     # DALL-E 3
IMAGE_API_PROVIDER=mock       # 占位图（开发用）

# 切换图生视频后端
I2V_API_PROVIDER=kling        # 可灵
I2V_API_PROVIDER=runway       # Runway Gen-3
I2V_API_PROVIDER=mock         # FFmpeg 静态图（开发用）
```

### 3.15 Agent SDK

`runtime/agent_sdk.py` 提供了 `BaseAgent` 抽象基类和 `AgentRegistry` 注册中心，是新 Agent 的标准扩展方式：

```python
from runtime.agent_sdk import BaseAgent, get_agent_registry

class MusicAgent(BaseAgent):
    name = "music"
    description = "Generate background music"

    async def execute(self, state: dict) -> dict:
        # 读取上游数据
        storyboard = state.get("storyboard", [])
        # 生成音乐
        music_path = await self._generate_music(storyboard)
        return {"music_path": music_path, "status": "music_done"}

    async def validate_input(self, state) -> bool:
        return "storyboard" in state

# 一行注册
registry = get_agent_registry()
registry.register(MusicAgent())
```

`to_agent_func()` 方法可以将 `BaseAgent` 实例包装为 `WorkflowEngine` 兼容的函数签名。

## 四、Workflow DSL（声明式工作流）

工作流通过 YAML 文件声明式定义，无需写 Python 代码。以 `comic.yaml` 为例：

```yaml
name: comic_drama
version: "2.0"
description: "Comic drama generation pipeline with image-to-video"

steps:
  - id: script
    agent: script
    depends_on: []
    produces_artifacts: [outline, episodes, characters]
    description: "Generate script with outline, characters, and episodes"

  - id: character
    agent: character
    depends_on: [script]
    produces_artifacts: [characters]
    description: "Enrich character visual descriptions"

  - id: storyboard
    agent: storyboard
    depends_on: [character]
    produces_artifacts: [storyboard, scenes]
    description: "Convert script to scene-by-scene storyboard"

  - id: image
    agent: image
    depends_on: [storyboard]
    produces_artifacts: [images]
    description: "Generate images for each scene via cloud API"

  - id: image_to_video
    agent: image_to_video
    depends_on: [image]
    produces_artifacts: [video_clips]
    description: "Convert images to video clips via cloud API"

  - id: voice
    agent: voice
    depends_on: [storyboard]
    produces_artifacts: [audios]
    description: "Generate voiceover for scenes via cloud TTS API"

  - id: video
    agent: video
    depends_on: [image_to_video, voice]
    produces_artifacts: [video_path]
    description: "Merge video clips, audio, and subtitles into final MP4"

quality:
  enabled: true
  check_after: [script, character, storyboard, image, voice]

director:
  enabled: false
  max_retries: 3
```

image_to_video 步骤在 image 完成后执行，将静态图片转为动态视频片段。voice 与 image_to_video 可并行（如 DSL 中声明 `parallel_group`），最终 video 步骤合并所有视频片段和音频。

WorkflowEngine 的拓扑排序算法会分析 `depends_on` 关系，自动生成最优执行顺序：

```
Wave 1: [script]
Wave 2: [character]
Wave 3: [storyboard]
Wave 4: [image]
Wave 5: [image_to_video, voice]     ← asyncio.gather() 并行
Wave 6: [video]
```

## 五、7 个 Agent 详解

### 5.1 Script Agent（剧本 Agent）

**职责**：根据用户创意和题材，生成结构化的剧本。

**输入**：`prompt`（创意描述）、`genre`（题材类型）

**输出**：
- `outline` — 故事大纲
- `characters` — 角色列表（姓名、性别、年龄、性格）
- `episodes` — 分集剧本（标题、摘要、完整剧本文本）

**技术实现**：
- 使用 LangChain `ChatPromptTemplate | ChatOpenAI | PydanticOutputParser` 链
- Pydantic 模型 `ScriptOutput` 强制结构化输出
- `@retry(3, exponential_backoff)` 自动重试，间隔 2-10 秒
- temperature=0.8（创意生成需要较高随机性）

**容错**：失败返回 `{"status": "error", "error": "..."}`，Director 可以决定重试或终止。

### 5.2 Character Agent（角色 Agent）

**职责**：将剧本中的基础角色信息丰富为详细的四维视觉描述，专门为图片生成优化。

**输入**：`characters`（来自 Script Agent 的角色列表）

**输出**：enriched `characters`，每个角色新增 `appearance` 字段：

```json
{
  "name": "林晓",
  "appearance": {
    "hair": "long flowing black hair with side bangs",
    "body": "slender figure, medium height",
    "cloth": "white summer dress with floral patterns",
    "face": "bright round eyes, gentle smile, fair skin"
  },
  "personality": {...},
  "catchphrase": "..."
}
```

**关键设计**：
- **英文描述**：appearance 字段使用英文，因为通义万相/DALL-E 等图片模型对英文 Prompt 效果更好
- **四维覆盖**：hair / body / cloth / face 四个维度确保角色外观完整
- **fallback 合并**：如果 LLM 输出不完整，自动与原始角色信息合并，确保不丢失数据
- temperature=0.4（需要精确输出）

### 5.3 Storyboard Agent（分镜 Agent）

**职责**：将每集剧本转换为逐场景的分镜描述，每个场景包含英文图片 Prompt、镜头类型、时长和台词。

**输入**：`episodes`（分集剧本）、`characters`（角色外观描述）

**输出**：`storyboard` — 场景列表，全局编号：

```json
{
  "scene_no": 1,
  "episode_no": 1,
  "prompt": "A young woman with long flowing black hair, wearing a white summer dress, standing in a sunlit ancient Chinese courtyard, wide shot, cinematic lighting",
  "camera": "全景",
  "duration": 5,
  "characters": ["林晓"],
  "dialogue": "这...这是哪里？"
}
```

**双策略容错**：
1. **策略 1**：PydanticOutputParser 强制结构化输出
2. **策略 2**（fallback）：如果策略 1 失败，使用 raw LLM 输出 + JSON 解析

每个场景的 Prompt 会自动注入相关角色的完整四维外观描述，确保图片生成时角色一致。

**集数控制**：通过 `settings.SCENES_PER_EPISODE` 元组控制每集场景数范围（默认 5-10）。

### 5.4 Image Agent（图片 Agent）

**职责**：为每个分镜场景生成对应的图片。

**输入**：`storyboard`（分镜列表）、`characters`（角色描述）

**输出**：`images` — 每个场景的图片路径列表，以及 `status`（`image_done` / `image_partial` / `error`）

**实现方式**：
- 通过云端 API 生成图片（DashScope 通义万相 / OpenAI DALL-E）
- 提交异步任务 → 轮询结果 → 下载图片文件
- 支持 base64 和 URL 两种返回格式
- 每张图片**自动降级**：API 失败时回退到占位图

**Mock 降级**：如果图片 API 未配置或不可用，自动生成 1024x1024 的彩色占位 PNG：
- 6 种颜色轮转（蓝、绿、橙、紫、红、青）
- 显示场景编号和 Prompt 前 80 字符
- 标注 "(Placeholder - API not configured)"

**部分容错**：某些场景图片生成失败不会终止整个流程，而是标记为 `image_partial` 继续执行后续步骤。

### 5.5 Voice Agent（配音 Agent）

**职责**：为有台词的场景生成语音配音。

**输入**：`storyboard`（含台词的场景）、`characters`（含性别信息）

**输出**：`audios` — 音频路径列表，`status`（`voice_done` / `voice_partial` / `error`）

**音色映射**：

| 角色性别标识 | 映射音色 | DashScope 语音 |
|-------------|---------|--------------|
| 男 / male / 男性 | male | longlaotie |
| 女 / female / 女性 | female | longxiaochun |

**实现方式**：
- 通过 DashScope TTS API 生成语音（异步任务 + 轮询模式）
- 支持同步和异步两种 API 响应模式
- 自动检测角色性别并匹配对应音色

**Mock 降级**：未配置 TTS API 时，自动生成静默 WAV 文件（22050Hz, 单声道, 16-bit），时长与场景 duration 一致，保证视频合成不会因为缺音频而失败。

### 5.6 Image-to-Video Agent（图生视频 Agent）

**职责**：将图片 Agent 生成的静态图片转换为短视频片段，为最终视频合成提供动态素材。

**输入**：`images`（图片列表，含路径）、`storyboard`（场景信息，含时长）

**输出**：`video_clips` — 每个场景的视频片段路径列表，`status`（`i2v_done` / `i2v_partial` / `error`）

**实现方式**：
- 通过云端 API（Kling 可灵 / Runway Gen-3）将图片转为视频
- 图片以 base64 编码提交，异步任务 + 轮询模式获取结果
- 下载生成的视频片段到本地 `video_clips/` 目录

**Mock 降级**：未配置 I2V API 时，通过 FFmpeg 将静态图片转为视频片段（`-loop 1 -t duration -c:v libx264`），保证后续视频合成流程正常工作。

**容错**：部分场景转换失败会标记为 `i2v_partial`，自动降级为 FFmpeg 静态图视频，不阻断管线。

### 5.7 Video Agent（视频 Agent）

**职责**：将图生视频片段和音频合成为最终的 MP4 漫剧视频。

**输入**：`video_clips`（视频片段列表）、`audios`（音频列表）、`storyboard`（场景信息）

**输出**：`video_path`（最终 MP4 文件路径）、`video_url`

**合成流程**（优先使用 image_to_video 产出的动态视频片段）：

1. **音频合并**：将配音合并到每个视频片段（`-c:a aac -b:a 128k -shortest`）
2. **字幕生成**：根据场景时长生成 ASS 字幕文件（Arial 48pt, 白色, 3px 描边, 底部居中）
3. **字幕烧录**：通过 FFmpeg 将字幕烧录到视频（`-vf ass=subtitle.ass`）
4. **拼接导出**：使用 FFmpeg concat demuxer 拼接所有片段为最终 `story.mp4`

**Legacy 模式**：如果没有 `video_clips`（未启用 image_to_video 步骤），自动回退到静态图片模式——将每张图片通过 FFmpeg 生成为视频片段后执行上述流程。

**时长处理**：使用 `ffprobe` 检测每个视频片段的实际时长（而非配置时长），确保字幕时间轴与视频精确对齐。

## 十二、关键设计亮点

### 12.1 部分重生成

这是 Runtime 最核心的用户体验特性。传统方案中，如果第 20 个场景的图片不满意，需要重跑整个流程。StoryFlow Runtime 通过 Session + Artifact 的组合实现了**从任意步骤恢复**：

```
用户："第 3 幕的图片风格不对，重新生成"

Runtime 内部：
  1. SessionManager.reset_from_step("image")
     → completed_steps: [script, character, storyboard]  (image, voice, video 被移除)
  2. ArtifactManager 加载 script/character/storyboard 的已保存结果
  3. WorkflowEngine 从 image 步骤开始执行
  4. 之前的 3 个步骤结果完全保留，不重新生成
```

### 12.2 事件驱动解耦

所有组件通过 EventBus 通信，没有直接依赖：

```
image_agent 不调用 voice_agent
         ↓
image_agent 返回结果 → WorkflowEngine 保存 Artifacts
         ↓
EventBus 发布 STEP_COMPLETED(image)
         ↓
voice_agent（如果已注册了事件监听）可以响应
但实际调度由 WorkflowEngine 负责
```

### 12.3 模型热切换

Adapter 模式让模型后端完全可插拔。要添加一个新的图片生成后端（如 Midjourney），只需：

1. 实现 `BaseAdapter` 子类
2. 注册到 `AdapterRegistry`
3. 配置环境变量

Agent 代码完全不动。

### 12.4 质量闭环

```
Agent 输出 → QualityEngine 检查
                │
                ├─ PASS → 继续下一步
                ├─ FAIL (score >= 0.7) → Director: RETRY
                ├─ FAIL (score < 0.3)  → Director: ROLLBACK
                └─ ASK_USER → 暂停等待人工
```

质量检查不是简单的"LLM 判断好坏"，而是**结构化的确定性检查器**，每个 Checker 针对特定维度、有明确的评分规则。
